# Why this Jarvis?

Research reviewed on **September 28, 2026**. The question was practical: how can a small macOS assistant turn everyday requests into useful actions while making its decisions understandable?

## The direction

Jev-Jarvis uses a bounded action catalog, a decision model that chooses from that catalog, and ordinary code that validates and executes the result. A separate planner can interpret more flexible phrasing. Voice is an input method; it is not the execution engine.

The distinguishing combination is **rehearsable missions, visible decisions, and explicit local/cloud choices**. These are product choices, not a claim that the individual ideas are new or that this is the first desktop assistant.

## What existing projects establish

| Project | Documented emphasis | What it informed here |
| --- | --- | --- |
| [Open Interpreter](https://www.openinterpreter.com/docs/desktop/approvals) | General computer operations with policies for approving sensitive changes | Show the actual change before executing a sensitive action |
| [OpenVoiceOS](https://www.openvoiceos.org/) | Custom voice interfaces, skills, and configurable speech engines | Keep speech separate from application capabilities |
| [Microsoft UFO](https://github.com/microsoft/UFO/blob/main/ufo/README_UFO_V1.md) | Agents that coordinate Windows applications and UI controls | Start with a smaller macOS adapter catalog that can be tested directly |

These projects have broader goals. This repository focuses on a personal laptop: opening an app, capturing a note, preparing a message, and running a familiar routine.

## Decision models have a specific job

TypeSafe's Jev returns a Choice, Score, or Noul over supplied state. It does not generate text or transcribe audio. This makes it suitable for questions such as “Which supported action is requested?” or “Which configured contact matches?” A message body or arbitrary program cannot be generated by asking Jev for a choice. [TypeSafe introduction](https://docs.typesafe.ai/introduction), [Jev with coding agents](https://docs.typesafe.ai/introduction/coding-agents).

Laya is an independent open-source decision engine from Convai Innovations, with local Python inference and similar primitives. It is not a TypeSafe product or a local distribution of Jev. Its official API provides both a single-checkpoint Agent and a Router that selects checkpoints. [Laya Python reference](https://nandhakishorm.github.io/laya/reference/).

The resulting design separates three responsibilities:

1. **Interpret:** rules or optional Ollama produce candidate action parameters.
2. **Decide:** rules, local Laya, or hosted Jev choose among supported actions.
3. **Execute:** application code validates arguments, applies policy, and calls a narrow macOS adapter.

Ollama supports JSON-schema-constrained responses, but structural validity does not establish that an action matches the request. Its output still passes through application validation. [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs).

## Features worth building around

- **Rehearsal:** see the proposed target and effect before touching the laptop.
- **Mission cards:** reusable routines with a preview of every constituent action.
- **Decision receipts:** expose the selected provider, interpreted intent, uncertainty, and execution outcome.
- **Recipient clarity:** show the resolved contact and exact message before sending; never pretend a send can be undone.
- **An honest offline baseline:** rules mode requires no model download, account, or API key. Local inference is optional; hosted inference is an explicit choice.

These are design priorities. The [README](../README.md) describes what the current implementation ships; ideas here are not a promise that every integration exists.

## Why macOS first

Apple documents interapplication automation through Apple Events and app-specific scripting dictionaries. Shortcuts supplies a supported command-line interface, including named shortcuts, input/output handling, and success/error exit codes. These are useful foundations for explicit adapters and user-configured extensions. They do not make every application universally scriptable. [Apple scripting architecture](https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/HowMacScriptingWorks.html), [Shortcuts command line](https://support.apple.com/en-au/guide/shortcuts-mac/apd455c82f02/mac).

macOS controls permission for one application to automate another. Installation of this project does not grant those permissions; users manage them in Privacy & Security. [Apple Automation settings](https://support.apple.com/en-ph/guide/mac-help/mchl07817563/mac).

## Limits that shape the design

Model confidence is not proof of correctness. Jev documents weaknesses with arithmetic, date comparisons, adversarial text, and irrelevant context. Those operations belong in code or need separate validation. [Jev known limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

Laya's own project reports checkpoint, language, context-length, and calibration limitations. We do not transfer benchmark scores into claims about Jarvis. A shared probability floor is a filtering policy; it does not establish equal calibration across providers. Keep command context short and candidate sets small. [Laya benchmarks and limits](https://nandhakishorm.github.io/laya/benchmarks/).

Confidence in the documented API shapes is high. Confidence in out-of-the-box command accuracy is unmeasured until evaluated on representative commands and the chosen model version. Mocked integration tests validate application behavior; they do not establish live model accuracy, latency, microphone quality, or message delivery.
